# `Fn` / `FnMut` / `FnOnce`

> **Level 6 — Closures & Functional Patterns**
> Closure traits: borrows immutably / borrows mutably / takes ownership (consumed on call).

---

## 2. Term Category

**Rust-specific (the closure bounds)**: In Rust, every single closure you write gets a unique, unnameable type generated by the compiler. Because of this, you cannot write `fn run(closure: Closure)`. You must use Generics and Trait Bounds! The compiler analyzes how your closure treats the variables it captures, and automatically implements one (or more) of three specific Traits (`Fn`, `FnMut`, `FnOnce`) for your closure. You use these traits to tell your functions what kind of closures they are allowed to accept.

---

## 3. Explanation

### (1) Design Motivation — "Why did we design this?"

When you pass a closure into a function, that function needs to know how dangerous the closure is. 

1. Does the closure just *read* the environment? If so, the function can safely call the closure 100 times in a loop.
2. Does the closure *modify* the environment? If so, the function can still call it 100 times, but it needs exclusive `&mut` access to do so.
3. Does the closure *consume* (take ownership) of a variable in the environment and destroy it? If so, the function can only call the closure **EXACTLY ONCE**! You can't destroy the same data twice.

To enforce this safety, Rust created three traits. When you write a function that accepts a closure, you use these traits as Trait Bounds (e.g., `F: Fn()`) to restrict exactly what kind of closures the function is allowed to run.

### (2) Reality Metaphor

Imagine you are managing a team of chefs (Closures).

- **`Fn` (Reads):** The chef looks at a recipe book. They can do this as many times as they want without destroying the book.
- **`FnMut` (Modifies):** The chef is mixing batter in a bowl. They modify the bowl. They can do this repeatedly, but they need exclusive access to the bowl while mixing.
- **`FnOnce` (Consumes):** The chef throws an egg into a frying pan. The egg is destroyed (consumed). The chef *cannot* throw that exact same egg into the pan a second time! A closure that consumes its environment can only ever be called exactly one time.

### (3) Rust Code Examples

#### Short Snippet (The Three Traits)
Here is how the compiler categorizes closures based on what they do inside their body.

```rust
fn main() {
    let text = String::from("Hello");
    let mut counter = 0;
    let data_to_destroy = String::from("Boom");

    // 1. Implements `Fn` (only borrows `text` immutably)
    let print_it = || println!("{}", text);

    // 2. Implements `FnMut` (borrows `counter` mutably)
    let increment = || counter += 1;

    // 3. Implements `FnOnce` (takes ownership of `data_to_destroy` and drops it)
    let destroy_it = || drop(data_to_destroy);
}
```

#### Fuller Example (Using them as Trait Bounds)
When you write a function that accepts a closure, you must specify which of the three traits you require using a Trait Bound.

```rust
// We require an `Fn` closure because we want to call it multiple times 
// without needing mutable access.
fn call_twice<F: Fn()>(closure: F) {
    closure();
    closure();
}

// We require an `FnOnce` closure because we only plan to call it once.
fn call_once<F: FnOnce()>(closure: F) {
    closure();
    // closure(); // ERROR! We cannot call an FnOnce closure twice!
}

fn main() {
    let my_name = String::from("Alice");
    
    // The compiler sees this closure only reads `my_name`, so it is `Fn`.
    // It perfectly satisfies both `call_twice` and `call_once`!
    let read_closure = || println!("{}", my_name);
    
    call_twice(read_closure);
}
```

## 4. Common Mistakes & Pitfalls

### Mistake 1: Misunderstanding Fn Traits Scoping and Lifecycle Rules

**The mistake:** Assuming Fn Traits instances remain valid beyond their declaring scope block or across asynchronous boundaries without explicit lifetime tracking.

**Why it's wrong:** Rust strictly enforces lexical scope boundaries and non-lexical lifetimes (NLL) at compile time. Accessing dropped values or failing to handle variable drop order results in compiler errors such as `E0597` or `E0382`.

*Incorrect:*
```rust
fn get_ref() -> &str {
    let s = String::from("fn_traits_data");
    &s // ❌ Error E0106/E0515: returns a reference to data owned by the current function
}
```

*Fix:*
```rust
fn get_string() -> String {
    let s = String::from("fn_traits_data");
    s // Ownership of the String is transferred directly to the caller
}
```

### Mistake 2: Mutating Fn Traits State Without Exclusive Ownership or `mut` Borrowing

**The mistake:** Attempting to mutate data associated with Fn Traits through an immutable reference `&T` or without specifying `mut` in variable declarations.

**Why it's wrong:** Rust's aliasing XOR mutability rule (`&T` for shared immutable access, `&mut T` for exclusive mutable access) prohibits mutating state through shared references unless interior mutability patterns (e.g. `RefCell`, `Mutex`) are explicitly used.

*Incorrect:*
```rust
fn update_val(data: &i32) {
    // *data += 1; // ❌ Error E0594: cannot assign to `*data`, which is behind a `&` reference
}
```

*Fix:*
```rust
fn update_val(data: &mut i32) {
    *data += 1; // Correct: exclusive mutable reference permits mutation
}
```

### Mistake 3: Concurrent Access to Fn Traits Across Threads Without `Send` / `Sync` Guards

**The mistake:** Sharing non-thread-safe Fn Traits instances across OS threads via `std::thread::spawn`.

**Why it's wrong:** Types that do not implement `Send` or `Sync` marker traits cannot safely cross thread boundaries. The compiler prevents data races by raising compile errors `E0277` (`trait Send is not implemented`).

*Incorrect:*
```rust
use std::rc::Rc;
use std::thread;

let rc = Rc::new(42);
// thread::spawn(move || { println!("{}", rc); }); // ❌ Error E0277: `Rc` cannot be sent between threads safely
```

*Fix:*
```rust
use std::sync::Arc;
use std::thread;

let arc = Arc::new(42);
thread::spawn(move || {
    println!("{}", arc); // Correct: `Arc` implements `Send` and `Sync`
});
```

## 5. Practice Exercises

### Exercise 1: Identify the Trait

**Problem:** Look at the three closures below. Based on what they do to the variables in their environment, identify whether the compiler will categorize them as `Fn`, `FnMut`, or `FnOnce`.

```rust
fn main() {
    let mut score = 0;
    let name = String::from("Player 1");
    let temporary_data = vec![1, 2, 3];

    // Closure A
    let closure_a = || println!("Welcome back, {}", name);

    // Closure B
    let closure_b = || { let x = temporary_data; }; // We assign `temporary_data` to `x`

    // Closure C
    let closure_c = || score += 10;
}
```

> [!check]- Answer
> - **Closure A is `Fn`**. It only reads (immutably borrows) `name`.
> - **Closure B is `FnOnce`**. By assigning `temporary_data` to a new variable `x` inside the closure, the closure takes Ownership of the vector. It can never do this a second time.
> - **Closure C is `FnMut`**. It modifies (mutably borrows) `score`.

### Exercise 2: Accepting `Fn` Trait Bounds

**Problem:** Write `fn exec_twice<F: Fn()>(f: F)` calling `f()` twice.

**Expected output:**
> [!check]- Answer
> ```
> Ping
> Ping
> ```
> ```rust
> fn exec_twice<F: Fn()>(f: F) {
>     f();
>     f();
> }
> fn main() {
>     exec_twice(|| println!("Ping"));
> }
> ```
>
> **Explanation:** `Fn` bounds accept closures that capture environment variables immutably and can be invoked repeatedly.

### Exercise 3: Consuming Environment with `FnOnce`

**Problem:** Pass a closure consuming an owned `String` to a function bounded by `F: FnOnce() -> String`.

**Expected output:**
> [!check]- Answer
> ```
> Consumed: hello
> ```
> fn consume<F: FnOnce() -> String>(f: F) -> String { f() }
> fn main() {
>     let s = String::from("hello");
>     let res = consume(move || s);
>     println!("Consumed: {}", res);
> }
> ```
>
> **Explanation:** `FnOnce` permits closures to transfer captured variable ownership out of closure bodies upon execution.

---

## 7. Key Takeaways

- **`Fn`**: The closure only *reads* its environment (`&T`). It can be called infinitely.
- **`FnMut`**: The closure *modifies* its environment (`&mut T`). It can be called infinitely, but requires mutable access (`mut closure`).
- **`FnOnce`**: The closure *consumes* its environment (takes ownership of `T`). It can only be called **exactly one time**, because the captured data is destroyed after the first call.
- You use these traits as Trait Bounds when writing functions that accept closures: `fn run_it<F: Fn()>(closure: F)`.
